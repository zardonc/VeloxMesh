支持原子版本校验的客户端仍使用每键串行队列，导致一个慢响应阻塞同一
provider 的后续请求。真实 Redis 对照中，后续发布等待从 **199.426 ms

它在物理上不可能实现。** 本轮不是完整 Phase 29 生产发布验收。

## 候选预算及 1.05 的解释

| 场景 | 候选条件 |
| --- | --- |
| 语义纯未命中／低命中 | 完整响应 P95 ≤ 两个 off 端点各自的 1.25 倍，且增量 ≤40 ms |
| 精确未命中 | 完整响应 P95 增量 ≤10 ms |
| 缓存命中 | P95 ≤60 ms，且 ≤两个对应 off 端点各自的一半 |
| 应用剩余耗时 | P95 ≤10 ms、P99 ≤15 ms |

这些是不同场景的条件；应用剩余耗时按逐请求扣除已测缓存／主模型阶段，
不等同于纯 CPU 执行时间。候选通过不覆盖业务语义质量、生产容量或授权。

Formal07 语义未命中相对 off 为 1.138–1.146 倍，低命中为 1.130–1.135 倍。
当 off P95 约130 ms 时，5% 只允许增加约6.5 ms，原 CPU 配置的 embedding
HTTP P95 约17 ms。其原始区间证据仍明确不满足1.05。

本轮逐请求拆分发现：除 embedding HTTP 外的缓存读取成本 P95 约2.64–2.66 ms；
嵌入解码／封装约0.33 ms；扣除嵌入、就绪检查和向量查询后的缓存调度成本
仅0.074–0.133 ms。即使在计算中把其他前台成本全设为零，只保留已测主模型
和嵌入耗时，其 pooled P95 仍约为 off 的1.083–1.099倍。
这是保持其他观测不变的敏感性分析，**不是硬件下界或可实现优化的预测**。

## 应用问题：同 provider 健康发布阻塞

新 GPU 网关小窗口先暴露了两条慢请求：

| 原始请求 | 观测 |
| --- | --- |
| off / diag-32 | 应用剩余16.704 ms，其中 `health_provider_sync` 为14.261 ms |
| off / diag-33 | 应用剩余16.328 ms，admission结束至主模型调用前等待约14.255 ms |

这些样本没有被剔除。源码检查确认旧的全局锁问题已修复，但
`RedisStore.publish` 仍持有同键发布令牌等待网络响应。真实 `RedisClient`
已实现 `OrderedSnapshotWriter`：Redis Lua 原子比较版本并拒绝迟到旧快照，
因此这一客户端不需要额外的同键网络串行等待。

先新增真实 Redis/TCP 延迟回归，再改产品源码。受控测试延迟首个响应200 ms，
以独立500 ms测试同步期限区分等待和超时，第二次发布应在40 ms以内完成。
测试参数只用于制造故障；生产默认同步期限仍为50 ms。

| 客户端 | 修改前 | 修改后 | 数据正确性 |
| --- | ---: | ---: | --- |
| 原子有序 Redis 客户端 | 199.426 ms，回归失败 | 1.312 ms，通过 | 本地与远端 pending 均为2 |
| 隐藏有序能力的真实 Redis 客户端 | 200.868 ms，串行对照通过 | 199.310 ms，仍串行 | 本地与远端 pending 均为2 |

实现只在客户端支持原子版本写入时跳过每键队列；仍在调用内同步、限时发布，
所有失败仍写日志。没有新增后台任务、无界队列、重试或忽略错误。
没有改变健康快照读取的失败关闭行为。

这一结果确认了应用的等待放大机制；不声称已经唯一归因生产环境每一次
Redis长尾，也不声称消除了发生延迟的原始请求自身的网络等待。

## 配置发现：独立 CUDA 服务

独立 CUDA 启动最初返回 `0xc0000135`。其 backend manifest 明确声明的
已安装 vendor DLL 目录未进入子进程 PATH；仅为任务子进程补充该目录后，
启动检查成功。没有改变全局 PATH、模型运行时默认值或系统电源设置。

同一份 Nomic v1.5 Q4_K_M 权重、同版本2.53执行路径的30请求筛查：

| 组件配置 | 成功 | HTTP P95 | 平均进程 CPU 核数当量 |
| --- | ---: | ---: | ---: |
| 独立 CPU 4线程 | 30/30 | 13.564 ms | 2.701 |
| 独立 CUDA12 | 30/30 | 4.382 ms | 0.021 |

这是两个部署配置的诊断，包含编译器、内核、设备与时钟状态差异；不是单因素
因果试验。GPU采样从P8/210MHz进入P3/1890MHz，显存增加，CPU使用显著降低。
30个测量请求另有每臂3个向量对照和2个预热，共70次组件调用。

三条同输入向量对照的 CPU/GPU 最低 cosine 为0.98516，不能混用现有向量集合。
GPU 网关诊断使用新测试身份和新 scope，300/300请求成功，embedding HTTP
P95为5.497 ms；但前后off P95从126.342降至101.667 ms，漂移19.53%。
on/off为0.963／1.197，不能挑选较慢的基线宣告1.05通过。
前置off应用残差P99为16.328 ms，也未满足该项候选门槛，并触发了上面的应用修复。

**GPU配置没有替换已验证的CPU配置。** 独立语义质量、低命中、长期稳定性和
正式验收仍未完成。这个低成本路径说明不能把1.05简单判作硬件物理不可能。

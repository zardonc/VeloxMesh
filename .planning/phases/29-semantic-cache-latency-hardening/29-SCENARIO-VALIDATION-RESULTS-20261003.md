# Phase 29：按场景验证结果（2026-10-03）

**正常应用处理指标通过本轮诊断预算；完整验收仍有未通过项，未合并 main。** 原低命中完整响应 P95 比值门槛 1.05 未通过；语义召回、部分写入残留及少量网关尖峰仍需跟进。不能把“正常网关处理快”替换成“所有功能与发布门槛通过”。

本轮根据引用任务「分析 Phase 29 遗留问题」制定并执行补充实验。[执行前计划](29-SCENARIO-VALIDATION-PLAN-20261003.md)的预算用于定位性能来源，不是已批准的生产 SLO。生产逻辑未修改，新增代码均为显式 opt-in 的真实测试基础设施。没有使用 mock embedding、mock聊天回答或 mock组件；延迟与断连用字节透明的 TCP 转发器作用于真实服务。

## 范围及可用性

应用路径：实际 App.New / Router → HTTP 认证 → semantic-cache eligibility / bounded lookup → 本地 embedding → Qdrant 查询及 SQLite记录 → 主模型路由/准入/HTTP调用 → 响应处理/结算 → 有界异步写入。实际 Redis、SQLite、Qdrant 均参与调用；PostgreSQL仅检查 readiness，本轮没有重新验证 pgvector 路径，也没有重跑 Phase 27/28 的全部协议矩阵。

测试前及最终链路复核确认组件和本地模型可用。本地聊天模型为 `qwen2.5-0.5b-instruct`；embedding 为 `text-embedding-embedder_collection`，另一款真实模型为 `text-embedding-nomic-embed-text-v1.5`。两款实际输出均为768维。第一次探测 nomic 约4.9秒，单列为冷启动，不混入稳定 P95。远程小批次采用 env.local 的免费 SANS `oc/mimo-v2.6-flash-free`，Gemini未重测。

负载包括六组独立应用/测试进程窗口，每组 direct/off/on/off-bare/on-bare 各100个请求（共3,000）；4/8/12/约16 RPS 的off/on各100；真实C4/C8突发、命中、旁路；10/20/50ms读预算；本机/VM embedding单独及聊天并行；双embedding模型同账户同数据库切换；跨进程冷集合；真实超时、断连、错误维度及Redis延迟；独立profiling与VM计数器。每项后端测试60秒硬截止。负载主要使用本地模型，远程调用仅用于小批次业务和可用性核对。

## 分场景 P95 结论

网关处理值从**同一个请求**的handler耗时中扣除完整主模型调用，eligible miss再扣除cache_read；没有用两个不同窗口的P95相减来计算网关开销。分位数采用 nearest rank。表中P99仅作为尾部补充，不用它替代P95。

| 场景 | 样本/指标 | P95 | P99 | 评测标准与结论 |
|---|---|---:|---:|---|
| cache-off，稳定8 RPS | 600，网关自身处理 | 4.640ms | 5.821ms | ≤10ms / ≤15ms：通过 |
| 正常 eligible miss，稳定8 RPS | 576，网关自身处理（24个hit另列） | 5.077ms | 7.786ms | ≤10ms / ≤15ms：通过 |
| 同上，缓存本地剩余处理 | 576，cache_read扣除前台embedding和vector_search的时间交集 | 0.077ms | 0.138ms | P95≤2ms：通过；该值包含未单独扣除的repo_read及调度，不是纯goroutine创建成本 |
| 同上，完整缓存读取 | 576 | 24.970ms | 27.905ms | 当前100ms读取预算+5ms容差：通过 |
| 不符合缓存条件的旁路，实际C4 | 100，网关自身处理 | 6.096ms | 9.009ms | ≤10ms / ≤15ms：通过；0 hit |
| 预热命中，相同问题、实际C4 | 100，完整响应 | 37.983ms | 55.078ms | ≤min(110ms, matched-off P95×0.5)=110ms：通过；100/100答案与真实种子相同，结算总数仅1 |
| 命中对照：同一固定问题，cache-off，实际C4 | 100，完整响应 | 246.547ms | 254.500ms | 命中窗口约为该基线的15.4%；基线结算101次（含warmup） |
| 突发，实际C8 | 100，网关自身处理 | 9.299ms | 12.653ms | P95≤10ms、P99≤15ms；主请求100/100成功，实际handler峰值8。完整响应P95=589.297ms，单列为饱和窗口 |

稳定窗口的主模型直连 / cache-off / cache-on 完整响应P95分别为 **126.828 / 131.741 / 160.744ms**。低命中率为24/600=4%；on/off比值 **1.22015**，六组分层bootstrap的探索性95%区间 **[1.08352,1.29043]**，仍超过原1.05门槛。六组都在同一次测试时段内，不能替代跨日环境样本；统计脚本保留固定seed和2000次重采样。

缓存开启确实引入了串行的embedding/向量读取等待，这是依赖调用耗时与缓存流程设计共同产生的端到端成本。当前没有网关本地处理成为主要瓶颈的证据，但不能据此删除上述真实增加的响应延迟。若正式验收改为绝对应用预算，应以业务场景/SLO明确替换旧标准；本轮只分开给出诊断结论。

| 开放到达负载 | off/on实际RPS | off/on发送积压P95 | 结论 |
|---|---|---|---|
| 4 RPS | 4.021 / 4.020 | 1.618 / 1.628ms | 维持负载，实际handler峰值1 |
| 8 RPS | 8.007 / 8.013 | 1.590 / 1.584ms | 维持负载，峰值2 |
| 12 RPS（83ms间隔） | 12.008 / 11.974 | 1.567 / 1.570ms | 维持负载，峰值4 |
| 约16 RPS（63ms间隔） | 15.316 / 15.563 | 217.588 / 103.849ms | 出现发送积压，不能据此声称维持目标负载；不能把不同到达负载的P95比值作为性能通过证据 |

C8突发出现4次lookup许可拒绝、2次读取超时及1次embedding错误观测（与超时事件可能重叠），主请求仍正常转发；后台101次写入（含种子）完成。冷集合的NotFound保留为vector_error观测，没有改写成普通miss。16 RPS和C8的主模型耗时明显增加，尚不能用单一模型容量证明网关最大吞吐。

## Embedding：排除错误的网络及观测器归因

最初本机Node客户端C4单独调用P95为38–51ms，VM Go客户端为100–110ms。这个对照同时改变了客户端和执行顺序，不能据此归因网络。补测相同Go适配器后，本机也出现相同长尾；反向执行bare→observed，长尾仍跟随第一个并发窗口，集中在前约10个请求。**没有证据认定这些约100ms尾部由网络或计时观测器造成。**

随后显式加入16次真实并发预热，预热样本单独保留，之后再测100个请求：

| 路径/并发 | 观测器开启P95 | 观测器关闭P95 | 结论 |
|---|---:|---:|---|
| 本机Go，C4 | 35.696ms | 38.618ms | 稳定窗口符合当前100ms读预算 |
| VM/SSH Go，C4 | 36.716ms | 37.304ms | 与本机接近，未发现显著稳定传输瓶颈 |
| 本机Go，C8 | 99.670ms | 99.715ms | 容量观察，接近100ms，不能批准扩大缓存并发 |
| VM/SSH Go，C8 | 76.858ms | 85.839ms | 容量观察；跨轮波动仍在，不能把独立窗口差值当作网络开销 |

所有结构化embedding压力样本均返回预期768维、有限且非零的向量；Go压力样本2,600个，本机Node压力样本1,400个，0失败。两款模型分别由真实probe确认维度。另用真实768维向量与767维配置测试，缓存拒绝读写、SQLite写入0行、主请求转发且只结算一次。

聊天并行窗口也完成，但当前worker等待聊天完成后才发下一个embedding，导致embedding到达率与单独窗口不同。它能证明共同运行的现象，**不足以量化同负载下的纯资源竞争**。首个并发窗口的瞬态已确认，究竟来自服务内部并行队列/模型状态、客户端连接启动或其他资源仍缺服务端日志，保持开放。稳定C4结果不能覆盖冷启动的100ms预算风险。

10ms读取预算使100个正式请求全部读取超时、0 hit；20ms窗口出现24次超时（含warmup）、3 hit；50ms窗口出现1次超时（含warmup）、正式请求4 hit。10ms时虽然主请求全部成功且完整响应较短，却丢失缓存作用并增加后台embedding，不能评为缓存性能通过或推荐上线参数。

稳定应用观测器开/关六组的平均完整响应差为off +0.224ms、on +0.829ms；独立窗口受主模型抖动影响，不能把差值精确视为埋点CPU开销。反向顺序及预热后的Go控制实验没有支持“观测器导致70ms长尾”的假设。

## 业务准确性及生命周期

双embedding模型：同一账户、同一SQLite数据库中，collection → nomic首次请求miss，各自真实写入后hit；切回collection复用原scope命中。两个不同模型ID的scope不同，切回原ID恢复原scope；两次种子调用产生两条usage。**补齐的是两个真实embedding模型生命周期，不再把第二聊天模型算作此项。** 两者恰好同为768维，未完成两个真实不同维度模型间切换；错误维度边界另行真实验证。

扩展诊断集由已有FAQ事实构造：正例10个基础问法×5种后缀=50，负例20个基础问法×5种后缀=100。没有用其替代未经提供的生产金标准，组合样本也不应当作50/100个独立业务意图。固定阈值0.92、不调整实现后结果：

| Embedding模型 | 正例命中/50 | 不同答案误命中/100 | 真实正例余弦范围 | 真实负例最大余弦 |
|---|---:|---:|---|---:|
| embedder_collection | 2 | 0 | 0.63766–1.0 | 0.81278 |
| nomic-embed-text-v1.5 | 9 | 0 | 0.74892–1.0 | 0.83177 |

直接向量的“余弦≥0.92”数量恰好为2/9，与网关命中数一致，指向模型、输入和阈值适配，不支持网关遗漏满足阈值的候选。正负分布有交叠，简单降低一个全局阈值不能同时达到全部同义命中与零误命中。召回不足仍是未解决项，不能靠修改验收数量隐藏。

三个事实的额外校验使用现有真实FAQ：14天试用、7天退款、取消后保留访问至账期结束。本地qwen0.5B在网关及绕过网关的直接请求中都把取消后访问时间答成 **“Paid access ends 7 days after a cancellation.”**，因此是上游模型回答错误，不能由网关猜测修正。SANS mimo模型的直连3/3及网关3/3事实正确；三个缓存响应与种子一致、usage为0，网关仅对三次上游调用结算。

## 故障及尖峰

- **重复embedding修复**：最终真实miss→异步Store→hit测试通过；正常完成Lookup只调用一次embedding，Store直接复用。透明网络实验在embedding完成前制造超时时允许后台重新embedding；在embedding已完成、search超时时验证Store无额外embedding。恢复后答案一致且结算一次。
- **Qdrant竞态**：两个独立OS进程，各16个并发创建者，共同创建真实冷集合通过；错误维度、错误distance、错误API key和取消均被拒绝，错误没有吞掉。
- **部分写入**：SQLite提交后断开Qdrant，保留Unavailable。恢复连接后第一次写入仍可能失败；后续真实请求约1.1秒内恢复写入及hit，所有主请求分别结算，无未索引记录误命中。初次恢复测试留下5条SQLite记录、仅1次成功向量写入，其余残留未自动回补/清理。恢复新请求不等于旧记录已经修复。
- **自然尖峰**：4 RPS cache-off出现18.219ms、20ms预算窗口出现19.642ms网关处理尖峰；两个请求的provider_complete结束→response_rules开始空档分别约15.727/16.184ms，结算自身仅0.324/0.474ms。因此不能直接归咎SQLite结算。源码该段包含health Redis同步、指标、路由记录及准入释放。延迟一次真实Redis响应200ms，实测该段空档202.932ms，证明同步Redis等待能产生此形态；尚未证明两次自然尖峰就是Redis导致。
- **独立profiling**：C8的100个请求成功，网关处理最大12.079ms，未复现>15ms。CPU采样650ms/6.69秒（约单核9.72%）；13次STW合计1.631ms、最大0.462ms；mutex累计10.96ms。VM四核计数器busy约7.62%、steal=0。它们不支持该profiling窗口持续CPU饱和，但不同场次不能用于排除自然尖峰中的GC/调度/Redis等待。旧93ms尖峰的准确根因仍未确认。

SANS完整同payload direct/off/on小批次中，direct warmup **12秒超时、HTTP status=0，没有上游错误响应**；错误为 `context deadline exceeded`。DNS约90ms，TCP约29ms，TLS约108ms，约228ms已完成request_written，剩余约11.77秒等待期间未观察到first_byte。请求完全绕过网关，故这次超时发生在上游/网络等待路径；缺少Provider后台日志，不能进一步判定模型处理、Provider排队还是中途网络。之后off/on四次请求及业务事实六次调用成功，不能继续把SANS一律归为“无资源”，也不能据此认定波动已消失。样本太少，不计算远程P95。

## 保留的问题及下一步

| 项目 | 当前结论 | 需要的下一步 |
|---|---|---|
| 原低命中1.05门槛 | 未通过；正常应用预算通过 | 按业务目标确认正式场景SLO，保留依赖等待及miss串行成本，不能直接覆盖旧门槛 |
| 语义召回 | 两款模型均不满足扩展同义集合 | 用业务确认的正负集校准模型/输入/阈值；有交叠时需要更明确的缓存适用范围，不能只降阈值 |
| Qdrant部分写入残留 | 无错误命中、恢复正常新写入；旧残留仍在 | 设计幂等回补或清理策略，再验证断连/恢复及TTL全流程 |
| embedding首个并发窗口 | 与网络/观测器简单归因不符；并发预热后稳定C4通过 | 补服务端队列、推理、GPU/CPU及模型加载日志，验证真实生产冷启动和突发策略 |
| post-provider尖峰 | 已定位时间段；Redis延迟能复现形态 | 为health同步/模型健康同步/指标/准入释放加可注入分段观测，关联同请求Redis等待与Go trace |
| 上游超时及小模型答错 | SANS等待路径超时；qwen0.5B直接答错；良好模型业务路径通过 | 保留Provider请求证据，选择符合业务事实质量的模型，后续获取服务端日志 |

因此本轮可以将**正常网关本地处理与已验证的业务链路**标为诊断通过；无法将整个Phase 29或分支发布标为全部通过。未合并main，未启用生产缓存或批准扩大并发/缩短截止参数。

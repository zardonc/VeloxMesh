# Phase 29：P95 门槛与下一步修正方向

日期：2026-10-03；核对代码：`780e12e`。状态：分析与候选方案，不修改正式验收合同、不批准生产启用。

## 判断

建议为快速本地模型重新定义分场景性能预算，但不能称原 `1.05×` 为“物理上绝对不可达”。当前证据证明：现有串行 embedding 路径在已测负载下未达到该预算；没有证明所有允许的实现、硬件和负载都无法达到。

下一步优先顺序：修正测量口径；限制不安全答案复用；并行拟定新的性能合同；再补充响应体超时与容量隔离。普通负载残余耗时小，不足以替代完整响应、语义正确性和饱和容量验收。

### 新发现：吞吐汇总错误

`evaluate.py:46` 用请求数除以样本的最大相对结束时间；`stable():74` 将六个各自从零计时的窗口合并后再次调用该函数，分子变为 600、分母仍约 12.5 秒，产生 `actual_rps≈48`。

按每条件 `总请求数 / 各窗口测量时长之和` 重算：off **8.017RPS**、on **8.001RPS**、memo **8.009RPS**。该值表示累计活跃测量窗口内的吞吐，不包含区组间准备时间。原报告的目标 8RPS 是正确的，汇总 JSON 的约 48RPS 不能用于容量结论。

该错误不改变排序得到的延迟分位数或原门槛失败结论。修正时应保留原评估文件，新建带方法版本的评估结果，并验证每窗口吞吐与汇总分母一致。

### 新重算：低命中整体与 miss 子集

原表包含每条件 600 次请求，其中 cache on/memo 各 24 次命中。整体 P95 与条件 miss P95 应分开报告。

本次按每区组客户端 `planned_ms` 筛选相同到达位置的 off 对照；不使用会因重复题目而重复的 `index`。这只是相同工作负载位置的匹配，不是同时执行的请求配对或主模型耗时因果证明。

## 为什么不能断言物理不可达

1. off P95 为 130.145ms，5% 增量预算只有 **6.507ms**；实测 embedding P95 约 21.5–21.7ms，说明现配置的预算很紧。但某阶段 P95 不是该阶段每次执行的硬下限。
2. 串行阶段的分位数一般不能相加减。完整响应还受主模型排队、缓存命中混合比例、资源竞争和时间区组影响；不能把 24.684ms 的完整 P95 差值说成 100% embedding。
3. 若假设同一主模型耗时分布，且每次 miss 必然增加固定 20ms，则纯 miss P95 约为 150.145ms，比值约 1.154。这证明的是该假设下不达标，尚未证明假设中的硬下限。
4. 若命中率为 4%，且命中耗时全部低于整体 P95，整体 P95 对应 miss 分布的 `(0.95−0.04)/0.96≈94.79%` 分位，不能直接当作 miss P95。
5. residual 含认证、路由、SQL/Redis 等等待，不是 CPU 时间。正常残余尖峰、冷态和 embedding 服务内部排队尚未闭环；约 5ms 不能证明优化已探底。

六区组探索性 bootstrap 比值区间均高于 1.05，支持“现配置实测稳定不达标”。证明某个固定部署下的工程下限，还需相同客户端、连接复用、模型热态、输入长度和到达率的联合时序，以及服务端排队/推理分段。即使补齐，也应限定部署和架构前提。

## 候选性能合同

不直接废弃历史 1.05，也不以本轮数据通过为唯一理由选门槛。先明确允许多少用户可感知延迟，再按部署类型冻结指标并在新一轮验证。

| 场景 | 建议候选指标 | 当前证据与边界 |
| --- | --- | --- |
| 固定普通负载的 application residual | P95 ≤10ms、P99 ≤15ms | 本轮通过；不是完整网关链路耗时，缓存前台等待另计 |
| 快速本地模型、纯 miss | `P95_on ≤ min(1.25×P95_off, P95_off+40ms)` | 比例与绝对增量同时满足；新重算子集符合候选，但需新的纯 miss 复测 |
| 固定低命中率完整请求 | 保留原 1.05 实测列，另列候选比例/增量及命中率 | 避免把整体数据改名为 miss；当前旧门槛仍失败 |
| warm hit | 保留当前 P95 ≤60ms 且 ≤matched off/2，以及 usage=0 | 本轮通过；是否收紧需独立复测与业务预算 |
| 慢远程模型 | 独立冻结增量、比例和业务完整响应 SLO | 不自动套用本地 1.25；同样要测主模型排队和失败 |
| 冷态、饱和、超载 | 单列总响应/排队/拒绝/恢复 SLO | 目前没有批准的饱和 SLO，不能用普通负载预算判通过 |

`≤1.25× 或 ≤off+40ms` 等价于使用两者较宽松的上限。off=2 秒时，它允许增加 500ms，而非 40ms。因此若目标是限制缓存前台惩罚，应使用同时满足，即 `min`。相同固定 20ms 增量的粗略比例预算在基线 ≥400ms 时才可落入 5%；这仍不是分位数测量的替代。

正式合同应绑定模型/权重与量化、输入输出长度、热态、到达率、实际并发、集合规模、命中率、计算口径和置信区间。修改时记录原失败证据及新合同的生效范围，性能、语义安全和隔离容量分别判定。

## 语义安全修正：优先 A，C 作附加过滤，B 暂作实验

### A：收紧已有可信 use-case 白名单，新增明确的复用模式

依据：当前 `Eligible` 已按可信 use case、API-key identity、目标模型和固定 system prompt 筛选；问题不是完全缺少白名单，而是被允许的政策 FAQ 仍可能误复用。模型和账户本身不能区分同一业务中的安全与危险问题。当前 memo 仅存向量，答案仍由语义检索选出。

操作：先让含政策期限、金额、否定、例外或个体条件的 use case 旁路答案缓存。随后设计服务端可信策略 `disabled / exact / semantic`；exact 模式校验完整问题指纹和现有 scope/版本/有效期，不能把向量 memo 当作精确答案缓存。semantic 仅开放业务明确允许同答案泛化的低风险静态 FAQ；未知策略保守旁路。暂不扩展到开放闲聊。

预期：7/8/14 天等改变答案的问题不复用旧答案；受限场景只在完整问题和 scope 匹配时命中，否则正常调用主模型。拒绝候选不等于请求失败。保留跨身份、知识版本、模型与设置隔离。

### C：可选的数值、实体、逻辑特征约束

依据：三个误命中直接涉及期限和相近问题，但简单比较数字不能覆盖否定、比较符号、单位或隐含时间。

操作：在受控 FAQ 域定义并版本化期限/单位、产品主体、否定、条件与比较关系；对候选和请求进行约束核对，无法解析或信息缺失即不复用。补充“七天/第八天/一周后”“以内/之后”“可退/不可退”、不同产品/币种等最小变化反例。种子问题没有数字而答案有期限时，必须借助可信 FAQ 元数据，不能仅做 query-token 相等检查。

预期：已知危险候选被阻断；可能降低召回。该机制是额外保护，不是逻辑等价或全域语义安全证明，不能单独批准政策类泛化。

### B：reranker 只作为有界实验

依据：[BGE 官方模型卡](https://huggingface.co/BAAI/bge-reranker-base#usage-for-reranker)描述的是 query/passage 相关性评分，不保证两问题具有同一个答案；相关性高仍可能含数值或否定冲突。额外串行模型调用也会增加预算。

操作：若 exact/旁路不能满足业务收益，使用独立 adapter 调用外部 reranker，保持网关不承担模型运行环境。先冻结“同答案可复用”的新标注集，单独评估误命中与召回；再测完整 miss/hit 延迟。设有界 top-k、deadline、并发与版本隔离，失败或超时拒绝缓存候选并转主模型。不能把 .80 或某个评分当作已验证默认值。

预期：仅在安全和收益都通过新留出集、且新增延迟符合合同后考虑采纳。旧 32 问已见，今后用作回归集，另建独立留出集；不反复调阈值后继续称其为独立验收。

## 超时和并发修正

当前 OpenAI adapter 使用 60 秒 `http.Client.Timeout`；现有 admission 控制 RPM，不等同于 in-flight 限制。主模型观测到最多四个活跃 slot，不证明硬件最优并发或配置上限就是四。先测容量曲线，再决定候选值。

超时应分层：连接/响应头、首个有意义的响应内容、流式空闲、总体 deadline。[Go 官方说明](https://pkg.go.dev/net/http#Transport)明确 `ResponseHeaderTimeout` 不覆盖响应体。此前上游首字节已到而响应体不完成的现象，不会仅靠响应头超时解决。5 秒只可作为某个 provider/profile 的候选；SSE 心跳不能无限重置首内容等待。

并发限制应围绕共享上游资源，在每个实际 provider attempt 前获取、结束/失败/取消时恰好释放一次；普通、SSE、工具流和 Fusion 分支均计入。选择快速拒绝或复用已有有界 Scheduler 排队，不增加多层无界队列。确认重试上限、流已输出后的重试禁令及计费归属，避免超时触发额外调用或重复结算。多网关进程须明确合计限制，单进程信号量不代表集群总容量。

结论：支持修订快速本地模型的性能合同，拒绝“物理绝对不可达”和“新门槛一改当前 Phase 29 全通过”两种表述。先关闭不安全答案复用，再用独立安全与性能证据决定是否恢复语义泛化；生产缓存保持关闭，白名单保持为空。
